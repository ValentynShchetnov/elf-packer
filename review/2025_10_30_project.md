## Project Overview

**Purpose**: elf-packer is an ELF binary packer that encrypts and compresses executables, embedding them with a custom unpacker stub that decrypts and executes the payload in memory using Linux's memfd_create syscall.

**Architecture**: Two-crate workspace
- **packer**: CLI tool (std) that reads ELF files, compresses with deflate, encrypts with ChaCha20Poly1305, and embeds into unpacker binary
- **unpacker**: no_std stub that reads itself, decrypts payload, decompresses, and executes in memory

**Development Timeline**: 4 days (Oct 26-30, 2025), single developer, 4 commits, 320 LOC

**Current State**: Prototype/MVP with critical bugs. Non-functional build system. Zero testing. No specification. Not production-ready.

## Technical Issues

### Critical Issues (7 total - 39h effort)

#### 1. Build Dependency on Pre-Built Unpacker Binary
- **Location**: packer/src/main.rs:28
- **Code**:
  ```rust
  static UNPACKER: &[u8] = include_bytes!("../../target/release/unpacker");
  ```
- **Issue**: Hardcodes path to unpacker binary in target directory. Packer cannot compile unless unpacker is already built. No build script enforces this dependency. Running `cargo clean` breaks the build entirely. Cargo workspace doesn't guarantee build order.
- **Impact**: Build system is fundamentally broken. New users cannot build project without manual intervention. CI/CD impossible without workarounds. Professional development workflows blocked.
- **Root Cause**: Embedding binary at compile time without build.rs dependency management
- **Effort**: 4h (create build.rs, use OUT_DIR, or switch to runtime linking)

#### 2. Memory Safety: Uninitialized Buffer
- **Location**: unpacker/src/main.rs:207-208
- **Code**:
  ```rust
  let mut buf: Vec<u8> = Vec::with_capacity(size);
  buf.set_len(size);  // Sets length without initializing memory
  let r = libc::read(fd, buf.as_mut_ptr() as *mut _, size);
  ```
- **Issue**: Creates vector with uninitialized memory via `set_len()`, then reads into it. If read is partial or fails, vector contains undefined data. Violates Rust safety guarantees even in unsafe code.
- **Impact**: Undefined behavior. Potential crashes, data corruption, security vulnerabilities. May work on some systems but fail unpredictably on others.
- **Root Cause**: Misunderstanding of Vec::set_len() safety requirements
- **Correct Code**: `let mut buf = vec![0; size];` or `buf.resize(size, 0);`
- **Effort**: 1h (trivial fix but critical bug)

#### 3. Misleading "No Encryption" Design
- **Location**: packer/src/main.rs:35-45
- **Code**:
  ```rust
  let key = match args.key {
      true => rpassword::prompt_password("Encryption key: ")?,
      false => "".to_string(),  // Empty key
  };
  #[allow(deprecated)]
  let cipher = ChaCha20Poly1305::new(&Sha256::digest(&key));  // Encrypts with SHA256("")
  ```
- **Issue**: When `--key` flag is false, uses empty string as password. Still encrypts file with SHA256("") as key. README claims "acts like original one" but anyone can decrypt with empty password. This is encryption with a publicly known key, not "no encryption".
- **Impact**: False security assumption. Users believe files are unencrypted when they're encrypted with known key. Security theater. Critical misunderstanding of security model.
- **Root Cause**: Design confusion between "no password" and "no encryption"
- **Correct Approach**: Add true no-encryption mode or remove option entirely
- **Effort**: 3h (refactor encryption to be truly optional)

#### 4. No Specification Document
- **Location**: Project root (missing spec.md or spec/)
- **Issue**: Binary format between packer and unpacker is completely undocumented. No formal specification of:
  - Binary format: marker position, hash format, nonce location, data layout
  - Offset calculations: why 60 bytes for hash, why 72 for data start
  - Versioning strategy: how to evolve format
  - Encryption parameters: algorithm choices, key derivation (or lack thereof)
  - Compatibility: between packer/unpacker versions
- **Impact**: Cannot verify correctness against requirements. Cannot extend safely. Cannot implement compatible tools. Cannot perform security review without reverse engineering code. Knowledge exists only in implementation.
- **Root Cause**: Implementation-first development without design documentation
- **Effort**: 6h (reverse-engineer format from code, document completely)

#### 5. No Automated Tests
- **Location**: Project root (missing tests/ directories in both crates)
- **Issue**: Zero test coverage. No unit tests, no integration tests, no test infrastructure. Cannot verify:
  - Pack/unpack roundtrip works correctly
  - Password verification is correct
  - Empty password mode behaves as documented
  - Error handling functions properly
  - Edge cases handled (empty files, huge files, corrupted data)
  - Memory safety (especially in unsafe unpacker code)
- **Impact**: Unknown correctness. 7 critical bugs remained undetected (memory UB, broken builds, security flaws). Cannot refactor safely. Cannot verify bug fixes. Production readiness unknown. Quality unprovable.
- **Root Cause**: No testing culture, prototype mentality
- **Effort**: 16h (create test framework, write comprehensive suite, achieve reasonable coverage)

#### 6. Deprecated Cryptographic API
- **Location**: packer/src/main.rs:40-41
- **Code**:
  ```rust
  #[allow(deprecated)]
  let cipher = ChaCha20Poly1305::new(&Sha256::digest(&key));
  ```
- **Issue**: Explicitly allows deprecated crypto API with `#[allow(deprecated)]`. Deprecated APIs may have security issues or be removed in future versions. Modern API exists but not used.
- **Impact**: Security vulnerability risk. Future incompatibility. Signals poor security practices. Professional security review would flag this immediately.
- **Root Cause**: Took shortcut with old API instead of reading current documentation
- **Modern API**: `ChaCha20Poly1305::new(key.into())` with proper key type
- **Effort**: 2h (update API usage, verify behavior unchanged, test)

#### 7. Weak Key Derivation Function
- **Location**: packer/src/main.rs:41, unpacker/src/main.rs:116
- **Code**:
  ```rust
  // Packer
  let cipher = ChaCha20Poly1305::new(&Sha256::digest(&key));  // Raw SHA256

  // Unpacker
  let cipher = ChaCha20Poly1305::new(&Sha256::digest(&key[..len]));  // Raw SHA256
  ```
- **Issue**: Uses raw SHA256(password) as encryption key. No salt, no iterations, no proper KDF (PBKDF2, scrypt, Argon2). Vulnerable to rainbow table attacks and fast brute force. Ironically, bcrypt IS used for password verification (lines 49, 114) but NOT for key derivation - inconsistent security model.
- **Impact**: Password security is weak. Pre-computed attacks possible. Professional penetration test would break this easily. Does not meet modern cryptographic standards.
- **Root Cause**: Security inexperience, didn't research proper KDF practices
- **Proper Approach**: Use PBKDF2/scrypt/Argon2 with salt for key derivation
- **Effort**: 4h (implement proper KDF, ensure compatibility, test)

## Architecture Assessment

### Strengths

**1. Appropriate Crate Separation**
- Clean separation: packer (CLI tool) vs unpacker (embedded stub)
- Distinct responsibilities: creation vs execution
- Good: Allows different optimization profiles

**2. no_std Optimization**
- unpacker uses `#![no_std]` with wee_alloc
- Minimizes binary size (critical for embedded stub)
- Shows: Understanding of size constraints

**3. Modern AEAD Cryptography**
- ChaCha20Poly1305 is excellent choice
- Authenticated encryption prevents tampering
- Industry-standard algorithm

**4. Compression Integration**
- Deflate compression before encryption
- Reduces payload size
- Correct order (compress-then-encrypt)

**5. In-Memory Execution**
- memfd_create for stealth
- No disk writes during execution
- Appropriate for packer use case

### Weaknesses

**1. No Format Specification**
- Binary layout undocumented
- Offset calculations hardcoded
- Cannot verify correctness against design

**2. Hardcoded Build Dependencies**
- packer:28 embeds unpacker binary via include_bytes!()
- Breaks clean builds
- No build.rs enforcement

**3. No Versioning Strategy**
- Cannot detect packer/unpacker incompatibility
- Cannot evolve format safely
- No migration path

**4. Duplicated Constants**
- NONCE_OFFSET, DATA_OFFSET not shared
- Changes require coordinated updates
- Error-prone maintenance

**5. Asymmetric Error Handling**
- packer: anyhow::Result
- unpacker: libc::_exit
- Cannot test unpacker errors
- Inconsistent philosophy

## Conclusion

elf-packer demonstrates solid architectural thinking (workspace separation, no_std optimization, modern crypto choice) but suffers from critical quality gaps. With 7 critical bugs including memory UB and broken builds, 0% test coverage, and no specification, the project is prototype-quality at best.

The root cause is clear: rapid prototyping (4 days) without quality investment. Development focused on features over correctness, resulting in 66 hours of technical debt for 320 LOC - more debt than development time.

**Path Forward**: Pause feature development. Fix critical bugs (memory UB, build system, security). Create comprehensive test suite. Document specification. Only then consider production use.

**Potential**: With quality investment, this could become a solid tool. The architecture is sound and the low-level implementation shows skill. Quality process is the missing piece.
